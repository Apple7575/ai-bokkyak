# 1분 복용 점검 — 서버 판정에서 빠진 조합 정리 (2026-09-10)

앱 안에 있던 **내장 규칙**(`care-app/src/lib/quickCheckRules.ts`, 약사 검수 전 상식 초안 27개)과
9월 6일부터 기본이 된 **서버 판정**(`quick_check_v1` → 약사 검수 DB, 게시 규칙 70~75개)을
같은 입력으로 하나씩 대조한 결과다. 검증 방법: 내장 규칙 27개의 (A × B)를 그대로 실제 서버
RPC에 보내 `findings`가 나오는지 확인 (`p_age`·`p_conditions`는 라벨이 연령·조건일 때 그 자리로).

관련 결정 문서: `docs/quick-check-rules.md`(내장 규칙 검수표), 검수 DB 원본: 루트 `약학검수시트.xlsx`,
`상호작용DB-v1-검토요청.pdf`.

### 약사 검수에 올릴 후보 (내장 규칙엔 있고 DB엔 없는 것)

내장 규칙의 근거 메모는 `docs/quick-check-rules.md` 표의 basis 열에 있다. 위 26개 중 (a)에 해당하는
것을 그대로 검수 요청 목록으로 쓰면 된다. 우선순위 제안:

1. 통증·소염제 × 혈압약, 60대 이상 × 통증·소염제, 신장질환 × 통증·소염제 — 어르신 대상 앱에서
   가장 자주 나올 조합이고 근거(NSAID·Beers criteria)가 확립돼 있다.
2. 마그네슘 × 갑상선약, 위장약 × 갑상선약 — 레보티록신 흡수 규칙이 DB에 이미 있으니 항만 추가하면 된다.
3. 종합비타민 중복 5종 — DB에 "중복 성분" 종류(relation_kind depletion/limit)가 있으므로 형식은 맞는다.
4. 임신·수유 중 × 혈압약·고지혈증약·여드름약, 간질환 × 고지혈증약·통증·소염제 — 조건 규칙. DB에
   간질환·수유 조건 자체가 없어 조건 추가부터 필요하다.

## 3. 반대로, DB엔 있는데 앱 칩으로는 안 걸리는 것 (배포 서버 v1 문제)

| 입력 | 서버 | DB 규칙 | 비고 |
|---|---|---|---|
| 위장약 + 마그네슘 | 0 | ppi_micronutrient_depletion | 5개 항을 전부 보내면 발화 → v1의 "전부 일치" 조건 때문 |
| 위장약 + 철분 | 0 | 같음 | 같음 |
| 고지혈증약 + 홍국 | 1 | red_yeast_rice_statin_duplicate | 정상 |
| 갑상선약 + 칼슘 | 1 | calcium_levothyroxine_absorption | 정상 |
| 아연 + 구리 | 1 | zinc_copper_depletion | 정상 |
| 고지혈증약 + 코엔자임Q10 | 2 | statin_coenzyme_q10_depletion **+ biotin_thyroid_lab_interference** | 코엔자임Q10이 칩이 아니라 제품명 부분일치로 잡혀 엉뚱한 비오틴 규칙까지 발화 |

저장소의 v2 SQL(`care-app/supabase/migrate-quick-check-rpc.sql`, 커밋 f87d226)은 "object 전부·precipitant
하나 이상"으로 바꿔 (b)를 고친다. **아직 서버에 반영되지 않았다.**

## 4. 칩 라벨이 서버에서 어떻게 풀리는지

`p_names`에 칩 하나만 보내 `resolved.via`를 확인했다.

| 칩 | via | 비고 |
|---|---|---|
| 오메가3·비타민D·마그네슘·종합비타민·철분·루테인·밀크씨슬·콜라겐·아연·홍삼·단백질보충제 | chip | 정상 |
| 갑상선약·혈압약·고지혈증약·위장약·통증·소염제·피임약 | chip | 정상 |
| 항우울제 | substance | 성분 1개(id 68)로 잡힘. 동작은 하나 종류명이 아니라 성분명으로 등록돼 있음 |
| **알레르기약** | chip, substance_ids = null | 칩은 있지만 성분 매핑이 없어 아무것도 대조되지 않음 |
| **유산균** | hff_product | 칩이 없어 이름이 비슷한 건기식 제품 하나로 잡힘(성분 4개) — 잘못된 판정 |
| **여드름약** | unresolved | 칩 없음. 결과 화면 "점검하지 못한 항목"에는 뜬다 |

서버 데이터(intake_class)에 유산균·여드름약 칩을 추가하고 알레르기약의 성분 매핑을 채워야 한다.
앱 쪽은 이 세 경우를 "점검하지 못한 항목"으로 표시하도록 바꿨다(같은 브랜치 커밋 참고).

## 5. 조건 라벨 대 DB 조건명

검수 DB에서 조건이 걸린 규칙은 8개뿐이고, 쓰는 조건명은 다섯 개다: 임신 · 만성콩팥병(3~4기·중증) ·
혈액투석 · 흡연 · 수술 예정 (PDF Q7). 배포 서버는 조건을 `name_ko` 글자 그대로 비교한다.

| 앱 버튼 | 보내던 값 | DB 조건명 | 처리 |
|---|---|---|---|
| 임신·수유 중 | "임신·수유 중" → 무시됨 | 임신 | 앱이 "임신"을 함께 보내도록 수정. 수유만 해당하는 사용자에게도 임신 규칙이 뜨게 됨 — 약사 확인 필요 |
| 신장질환 | "신장질환" → 무시됨 | 만성콩팥병(3~4기·중증) / 혈액투석 | 뜻이 달라 자동 연결하지 않음. 결과 화면에 "아직 서버 점검에 반영되지 않은 항목"으로 표시. 약사가 "신장질환 전반" 조건을 추가하거나 버튼을 DB 뜻에 맞게 바꿔야 함 |
| 간질환 | 무시됨 | (없음) | 위와 같이 표시 |
| 60대 이상 (연령) | "60대 이상" → 무시됨 | (고령 규칙 없음) | 위와 같이 표시 |
| 해당 없음 | "해당 없음"이 조건으로 전송됨 | — | 보내지 않도록 수정 |

## 6. 재발 방지

`cd care-app && npm run check:server` — 실제 RPC에 대고 (1) 모든 칩이 chip/substance로 풀리는지,
(2) 조건 별칭마다 발화 증거(홍국+임신 → pregnancy_red_yeast_rice)가 있는지, (3) 철분+갑상선약
같은 기준 조합이 살아 있는지 확인한다. 네트워크가 필요해 jest에 넣지 않았다. 오늘 기준으로는
알레르기약·유산균·여드름약 때문에 실패(exit 1)하는 것이 **정상**이며, 서버 데이터를 고치면 통과한다.
